# 热更补丁操作手册（flutter_patcher）

> TODO 适用于 Android 与 iOS。商店版本唯一来源是 `pubspec.yaml`。当前项目通过 `vendor/flutter_patcher` 固定 1.1.0 的项目内编译兼容修复，不能绕过该依赖直接使用全局版本。

## 更新边界

- 现有不支持热更的线上包必须先通过应用商店安装一次新宿主包；不能给旧包直接补上热更能力。
- 当前工具的 Android 热更目标为 Android 9+、`arm64-v8a`；本轮 iOS 验证目标为 `ios-arm64` 真机。其他设备范围不能由模拟器或本轮结果推定。
- 可更新 Dart 代码、兼容的纯 Dart 依赖，以及新增/修改的资源。原生插件、FFI、Flutter SDK 变更和删除资源必须整包发版。
- 使用 `flutter_patcher build` 构建宿主；普通 `fvm flutter build` 的产物不作为热更正式宿主。
- 第一次冷启动检查、下载和安装，下一次冷启动才运行补丁；不会强制重启用户正在阅读的 App。
- 商店版本（如 `1.2.3+25`）、签名文件序号 `seq`、展示用的 `hotfix_version` 是三个概念。打补丁不改变商店版本；脚本在登记事务中自动递增热更版本，设备只安装更高 `seq`；重复提交同一已接受文件按幂等处理，低序号不能覆盖新补丁。
- 关于页只显示本次原生诊断确认实际加载的热更版本，待生效补丁不提前显示。自动停用、整包升级丢弃后不再显示旧热更版本。

## 环境与存储

所有 Flutter/Dart 命令通过 FVM 执行。脚本从同级后端 `config/data_environment.js` 读取数据库配置，从所选库的 `image_config` 读取 OBS endpoint、AK/SK、桶名和公开域名；不修改全局 AWS 配置，也不输出密钥。

以下 `--prod` 命令需先建立生产数据库 SSH 隧道，并用 `HOT_PATCH_BACKEND_DIR` 指向本机独立发布配置；端口可通过 `database_port` 设置，例如 13306。此准备完成后，补丁生成、上传和入库仍由一条命令执行。

```bash
fvm flutter pub get
fvm dart run scripts/hot_patch.dart check --local
fvm dart run scripts/hot_patch.dart check --prod
```

- `--local` 为默认环境：读取本地配置、本地独立 baseline、OBS `flutter_patcher/verification/` 对象前缀。本轮实际本地 schema 是 `top_read`，连接主机为 loopback；不能仅凭数据库名称判断是否生产。
- `--prod`：生产数据库及 `flutter_patcher.yaml` 中的持久 OBS baseline；写入前确认，自动化时显式加 `--yes`。
- 可用 `--baseline-store file:///真实绝对路径` 指定验证用 baseline；不要与线上版本共用试验基线。
- 如终端代理导致 OBS 大文件断流，可显式设置 `HOT_PATCH_OBS_DIRECT=1` 仅让本次脚本直连 OBS；不修改全局代理。
- OBS 全程使用校验证书的 HTTPS。带点号桶名通过区域 TLS 端点与虚拟 Host 处理，不降级 HTTP、不关闭证书校验。
- 基线与补丁使用 OBS 原生 `x-obs-forbid-overwrite` 原子禁止覆盖，并回读 SHA256。桶启用/暂停多版本时该头不保证禁止覆盖，脚本会拒绝写入。
- 云端补丁对象名包含北京时间 `YYYYMMDD_HHMMSS` 与随机后缀，避免同秒覆盖。数据库 `file_name` 仍保留 SDK 规范名称，不能把时间戳塞进宿主目标文件名。
- 私钥保存在 `~/.flutter_patcher/keys/`，需离机加密备份；基线和私钥不可丢失。公开 `flutter_patcher.yaml` 不含私钥。

## 先部署后端，再上架新宿主

后端可先部署，现有线上客户端不调用新增补丁接口，不会因此获得热更。生产操作由发布者执行：

1. 备份已有热更表；在后端目录执行迁移（新增表/列/索引，支持重复执行）：

   ```bash
   node database/migrations/20261110_app_patch.js --production
   ```

2. 部署 `routers/app_patch/`、`routers/admin_patch/`、`utils/patch*.js`，以及 `config/don_check.js`、`config/fuzzy_token_check.js`、`config/no_encryption_url.js` 的补丁接口配置，重启后端。
   若后端进程也继承了会导致 OBS 大文件断流的代理，可为该进程设置 `PATCH_OBS_DIRECT=1`。此开关仅直连 `image_config.domain_name` 所配置的 HTTPS 域名及路径范围，拒绝重定向，仍校验证书和文件 SHA；不修改全局代理，也不向下载请求附加 OBS 密钥。默认不开启。
3. 部署后台补丁管理页，为超管配置 `app_patch` 菜单。无需新增 Node 依赖。
4. 从本地新宿主验证生产 URL 的检查、下载、诊断接口后，再上架两端新版本。

最终迁移会保留历史诊断和安装行，按身份已核对的成功补丁报告去重重建安装数，修正旧协议误计；重复执行不会累加。若在本轮最后计数修复之前已部署，请再同步 `utils/patch_boot_report.js` 与 `database/migrations/20261110_app_patch.js`，执行迁移并重启进程。

正式 App 默认请求 `https://app.read.top`。普通 Flutter 调试可通过 `--dart-define=API_BASE_URL=http://本机IP:5016` 显式覆盖。热更工具 1.1.0 不支持传递任意 dart-define，本轮真宿主验证使用独立源码副本配置本地 URL；不得将该验证副本作为商店包。

## 构建正式宿主

```bash
# 双端、递增版本、记录持久 baseline；iOS 默认 app-store 导出。
fvm dart run scripts/hot_patch.dart release --prod --os both --bump patch --yes
```

Android 默认同时生成 AAB 与 APK：AAB 用于 Google Play，APK 用于其他支持该格式的渠道。Google Play 的 App Bundle 要求见 [Android 官方文档](https://developer.android.com/guide/app-bundle)。仅需 APK 时使用 `--android-format apk`；该选项只适用于 `release`。`make release-android` 同样默认双产物，可用 `ANDROID_FORMAT=apk` 覆盖。

脚本打印每端确切产物位置：`.dart_tool/flutter_patcher/releases/<时间戳-平台>/app-release.apk`、`app-release.aab`、`app-release.ipa`。以该路径及同目录 `build.json` 为准；不要到 `build/app/outputs/flutter-apk/` 找旧包上架。

AAB 与 APK 来自同一受控构建副本，共用经过校验的宿主引擎、代码、信任配置和资源；AAB 另外校验 manifest、架构和 JAR 签名。APK 的原始 baseline 保持为真值，AAB 回执单独记录。工具优先使用已有 Gradle 缓存中的 bundletool；也可显式设置 `BUNDLETOOL_JAR` 为已准备好的官方 all.jar，或设置 `BUNDLETOOL_CLASSPATH`。脚本不会自动安装工具。

Android 发布构建仅包含完整可运行的 arm64 架构，并校验每个原生库的全部 ELF 加载段、APK ZIP 对齐和 AAB `PAGE_ALIGNMENT_16K`。项目内热更启动库已添加 16KB 链接参数；原生变化必须随新宿主发布。页大小要求见 [Android 官方说明](https://developer.android.com/guide/practices/page-sizes)。

记录商店版本/build、Git 提交/tag、平台、宿主 fingerprint、基线位置及签名公钥。构建失败或 baseline 未成功记录时不得上架。

本地开发签名验证可使用 `release --local --export-method development --channel verification`；`release` 确认后会递增版本。验证工程与线上工程使用不同 baseline 位置。若取消，版本保持不变。

## 一条命令生成双端补丁草稿

在对应正式宿主的代码版本上修复 Dart/资源，保持 `pubspec.yaml` 的版本不变：

```bash
fvm dart run scripts/hot_patch.dart patch --prod --os both --remark '修复具体问题' --yes
```

脚本自动：读取 build → 分别生成两端补丁 → 校验签名存在性/格式/目标/内容哈希 → 获取 `image_config` → HTTPS 不可覆盖上传 → 回读校验 → 事务登记草稿并自动分配热更版本。

- 默认双端，单端使用 `--os android` 或 `--os ios`。
- 默认当前 build；补旧版时先检出对应代码，再用 `--vc N` 明确目标。
- 使用 `--file <SDK规范名称.fptc>` 跳过构建，仍执行上传与登记。相同文件重复运行按幂等处理，不重复上传或增加热更版本。
- 同目标同 `seq` 不同内容拒绝登记，不覆盖已发布文件；失败后可重试。已删除记录不会被脚本自动复活。
- `--dry-run` 只校验计划/已有文件，不构建、不连接数据库、不上传、不改版本或全局配置。
- 脚本始终只登记草稿，不通过命令行直接把补丁变成灰度或全量。

## 灰度、全量与诊断

后台状态：草稿不下发；灰度按稳定设备 ID 分桶；全量全部下发；下线停止后续下发。

1. 脚本登记双端草稿后，核对宿主/build/平台/热更版本。
2. 后台先设灰度 10%，观察成功/失败设备数、启动健康率和「启动诊断」记录，再逐步提高到 25%、50%、全量。
3. 相同设备分桶稳定；扩大比例时覆盖集合单调增加。新补丁未命中灰度的设备可以继续得到之前的可用全量补丁。
4. 健康报告在首帧后累计前台 5 秒再发送；报告使用原生实际 seq/目标包/诊断时间绑定身份，重试不重复计安装数。历史缺少身份的报告在后台标注，不能混作已核对诊断。整包升级正常清理旧补丁保留为中性诊断，不计入补丁启动失败或健康率分母。
5. 灰度调回 0% 或下线只停止新下载，不会卸载已安装补丁；撤回已装补丁必须发布签名回滚文件。

## 一条命令生成回滚草稿

```bash
fvm dart run scripts/hot_patch.dart withdraw --prod --os both --remark '撤回具体补丁' --yes
```

脚本生成更高序号的签名空 payload 文件，上传并登记回滚草稿。后台选择「发布回滚」才激活；后端校验回滚序号高于同宿主所有曾发布的序号，在同一事务内全量激活回滚并下线旧补丁。

陈旧回滚文件会被拒绝，不能通过点击旧补丁绕过该校验。回滚后的设备下次冷启动运行原版；需要恢复某个历史好版本时，在好代码上重新生成更高 `seq` 的新补丁，不要重传旧文件。启动失败保护只针对 SDK 能检测的启动/加载错误，仍需真实设备验证和正常崩溃监控。

## 验证与故障排查

本轮 TopRead 已在 Android ARM64 的 4KB/16KB 模拟器及 iPhone/iPad 真机完成验收：灰度、A→B 连续补丁、待生效与实际版本、错误签名/旧序号拒绝、签名撤回、坏启动自动停用、保留数据的整包升级清理均通过。AAB 还完成真实分包安装与热更/撤回，16KB 环境关闭兼容模式并核对进程实际页大小。测试发布均已下线，设备保持无测试标记/Hotfix 的稳定基线。

主源码仍为 `1.2.3+25`；build26/27/28 仅用于隔离验收。生产域名四项接口冒烟通过，未发布生产补丁；完整原生闭环使用独立本地库。正式发布前按上文同步最终后端、准备数据库隧道并生成正式宿主，不能上架本轮使用局域网 URL 的测试包。

```bash
fvm dart analyze lib/services/patch lib/api/patch.dart lib/models/patch_check_result.dart scripts
fvm flutter test --no-pub test/services/patch test/models/patch_check_result_test.dart test/api/patch_report_test.dart test/scripts
# 后端目录：独立本地 MySQL 测试库，保留测试结果，不触碰生产库。
PATCH_LOCAL_MYSQL_TEST=1 node --test test/app_patch.test.js
# OBS 原子禁止覆盖的独立前缀测试，保留对象。
fvm dart run scripts/verify_obs.dart
```

若后端当前配置已切换至服务器，测试会在连接前拒绝非 loopback 地址。可用 `PATCH_TEST_ENV_FILE=/独立本地配置/data_environment.js` 明确选择本地配置；发布脚本可用 `HOT_PATCH_BACKEND_DIR=/独立本地后端配置目录`。不要为了测试覆盖正在部署的配置，也不要用 `--local` 指向服务器数据库。

正式发布脚本的数据库连接仅允许 loopback。当前使用的 MySQL 驱动不能验证远端证书，且本轮公网 MySQL 实测未启用 TLS，因此生产访问通过保留主机密钥校验的 SSH 隧道。服务器自身使用的内网地址不一定能从发布电脑访问；发布电脑使用独立配置目录，顶部 `database_address` 值设为 `127.0.0.1`，并添加 `let database_port = 13306`，再通过 `HOT_PATCH_BACKEND_DIR` 指定。生产账号、库名、密码沿用实际生产配置；本地模式仍使用独立本地库。配置文件含凭据，应仅本机账户可读。

上线前必须逐端验证：未命中灰度/命中灰度、下载后不提前生效、冷启动运行变更、连续补丁、低序号拒绝与同文件幂等、错误签名拒绝、签名撤回、启动失败停用、整包升级清理，以及真实 API 启动诊断归属。单元测试、后端格式测试、示例工程成功均不能替代 TopRead 真宿主验收。

- `BASELINE_NOT_FOUND`：环境/store/build/flavor 不一致，或该包没有记录基线。
- `BASELINE_RELEASE_CONFLICT`：同宿主标识试图记录不同内容；正式发版递增 build，不能覆盖基线。
- `BUILD_PROJECT_INVALID` 软链：通过脚本或 `make release-* / patch-* / withdraw-*` 运行；包装器会互斥暂存工具目录并在退出时恢复，冲突时保留两份文件报错。
- 托管 SDK 存在修改：先审查、备份并恢复；脚本仅检测，不自动改 SDK。
- `Expected instance member ...ToolbarButton.text`：确认使用项目内 `vendor/flutter_patcher` 及锁文件。不要手工改 Flutter SDK 构造函数名。
- `cupertino_icons/lib` 不存在：该包只有资源，这是合法结构；项目内工具已跳过不存在的 Dart 源目录，不能创建假 `lib` 目录绕过校验。
- Flutter 3.47.9 的 AAB 日志出现 `failed to strip debug symbols`：该版本会把已预先剥离的引擎误判为缺少符号。项目内工具只对这一精确错误及新产物启用兼容路径，仍需通过全部 ELF、内容、签名、manifest 和页对齐校验；成功回执含 `android_bundle.build_compatibility = flutter-3.47.9-prestripped-engine`。其他构建错误仍失败，不修改 Flutter SDK 或伪造符号文件。
- Android 模拟器访问本地 API 失败：模拟器进程会继承宿主 `http_proxy`，即使 Android 设置显示无代理，也可能把局域网请求转给代理。重启专用测试模拟器时仅清除该进程的代理环境变量，保留全局配置及 userdata。
- 密钥丢失/泄露：旧宿主无法安全换钥；生成新钥并发布新宿主包。
